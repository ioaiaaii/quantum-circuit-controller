# Code-vs-Docs Audit — 2026-05-21

This is a point-in-time audit of the QCC codebase against both doc trees. It is not live documentation; treat it as a punch list.

## Scope and framing

- Audit target: `internal/`, `cmd/`, `api/`, `qcc-executor/src/`, `proto/` against `docs/systems-design/` and `docs_revisited/`.
- Source-of-truth precedence (per [`../../docs_revisited/README.md`](../../docs_revisited/README.md)): code first, then `docs_revisited/`, then `docs/systems-design/`.
- QCC is a thesis proof-of-concept. Known unfinished areas (scoring-based selection, Kubernetes Event emission, distributed tracing, executor-side OTel, async restart tolerance, QRMI adapter, per-QPU credential references, Helm packaging) are *expected* and already disclosed honestly in the implementation status section of [`../../docs_revisited/README.md`](../../docs_revisited/README.md#implementation-status). They are **not** re-reported here.

## 1. Doc claims not backed by code

Three places in `docs/systems-design/` describe runtime behaviour the code does not deliver.

### 1.1 `QCC-System-Design.md` §8 lifecycle diagram is missing the `Scheduling` phase

The mermaid state diagram at [`QCC-System-Design.md`](./QCC-System-Design.md) lines 287–303 has no `Scheduling` node or transitions.

The code drives `Pending → Scheduling → Succeeded`:

- `PhaseScheduling` constant: [`../../api/v1alpha1/circuit_types.go:86`](../../api/v1alpha1/circuit_types.go)
- Transition logic: [`../../internal/controller/circuit_controller.go:446`](../../internal/controller/circuit_controller.go)

§10.4 of the same doc (line 363) and §3 of [`QCC-API.md`](./QCC-API.md) both describe the phase correctly — only the §8 diagram is stale.

### 1.2 `QCC-System-Design.md` §7.1 claims a per-QPU calibration cache with 60s TTL

[`QCC-System-Design.md`](./QCC-System-Design.md) line 281 states:

> "Calibration metadata is cached per-QPU with a configurable TTL (default: 60 seconds) to bound the rate of external metadata fetches under load."

No such cache exists. `ProbeBackend` runs once at QPU registration, gated by `qpu.Status.Qubits == 0` at [`../../internal/controller/qpu_controller.go:80`](../../internal/controller/qpu_controller.go).

[`QCC-Design-State.md`](./QCC-Design-State.md) line 80 correctly classifies the TTL cache as future work (`🪪`).

### 1.3 `QCC-System-Design.md` §15 refers to `status.queuePosition`

[`QCC-System-Design.md`](./QCC-System-Design.md) line 439 says:

> "QCC doesn't model it beyond reporting `status.queuePosition` from the vendor's stream."

No `QueuePosition` field exists on `Circuit.status` — see [`../../api/v1alpha1/circuit_types.go:319–395`](../../api/v1alpha1/circuit_types.go).

Vendor queue position is surfaced only as a free-form `WatchTaskResponse.message` string at [`../../qcc-executor/src/qcc_executor/servicer.py:606–612`](../../qcc-executor/src/qcc_executor/servicer.py).

[`QCC-Design-State.md`](./QCC-Design-State.md) line 124 and [`../../docs_revisited/api.md`](../../docs_revisited/api.md) both describe the stream-message-only behaviour correctly.

## 2. Code features not documented (or under-documented)

### 2.1 Method-pinned Aer variants

[`../../qcc-executor/src/qcc_executor/adapters/aer.py:66–73`](../../qcc-executor/src/qcc_executor/adapters/aer.py) registers six pinned methods:

- `aer_statevector`
- `aer_mps`
- `aer_stabilizer`
- `aer_extended_stabilizer`
- `aer_density_matrix`
- `aer_unitary`

[`../../docs_revisited/README.md`](../../docs_revisited/README.md) line 27 and [`../../docs_revisited/architecture.md`](../../docs_revisited/architecture.md) line 107 mention only "method-pinned variants such as `aer_statevector`". Minor — only a problem if a reader wants the full set.

### 2.2 `ReasonScheduleProduced` condition reason

Defined at [`../../api/v1alpha1/circuit_types.go:143`](../../api/v1alpha1/circuit_types.go), used at [`../../internal/controller/circuit_controller.go:854`](../../internal/controller/circuit_controller.go) for the `Scheduled` condition.

Not listed in [`../../docs_revisited/api.md`](../../docs_revisited/api.md) "Common Failure Reasons" (it's a success reason, so understandable) and not in [`QCC-API.md`](./QCC-API.md) §5.2's "Recommended reasons" table either. An omission, not a contradiction.

### 2.3 Possible probe-on-every-reconcile loop for generic local QPUs

[`../../internal/controller/qpu_controller.go:80`](../../internal/controller/qpu_controller.go) sets `needsProbe = (Availability == Available && Status.Qubits == 0)`.

For a `provider: local` QPU resolved to a bare `AerSimulator()`, [`../../qcc-executor/src/qcc_executor/adapters/aer.py:209`](../../qcc-executor/src/qcc_executor/adapters/aer.py) may return `num_qubits=0` because the attribute is often missing on a plain `AerSimulator`. [`../../internal/controller/qpu_controller.go:137`](../../internal/controller/qpu_controller.go) only assigns when `p.NumQubits > 0`, so the value stays at zero, the gate stays true, and every reconcile re-fires `ProbeBackend`.

Not load-bearing for `fake_*` / IBM QPUs that report a real qubit count. None of the docs flag the loop case.

## 3. Internal inconsistencies between the two doc trees

Beyond the deliberate design-vs-implementation split, the trees largely agree. The only material disagreement is the same item from §1.3 above — `QCC-System-Design.md` references `status.queuePosition`; all of `QCC-API.md`, `QCC-Design-State.md`, and `docs_revisited/api.md` disagree.

`QCC-API.md` §3.5 ("`traceId` is reserved") and `docs_revisited/api.md` ("reserved, not populated today") agree — no issue.

## 4. Simplification opportunities in `docs_revisited/`

The blunt feature-list register drifts in a few places. Each spot below restates content that the surrounding diagram or table already conveys.

### 4.1 `architecture.md` "Mode Flows" duplicates the Mode/RPC matrix

[`../../docs_revisited/architecture.md`](../../docs_revisited/architecture.md) lines 163–231 spell out each mode as a separate subsection. The Mode/RPC matrix at lines 183–188 already conveys the dispatch. The `mode=run` subsection re-explains the sync/async branch that the sequence diagram at lines 125–161 immediately above already shows.

Cutting "Mode Flows" entirely and adding one line above the matrix would save ~70 lines without losing operational facts.

### 4.2 `observability.md` metric inventory triplicated

[`../../docs_revisited/observability.md`](../../docs_revisited/observability.md):

- Lines 88–95 — bullet list of metrics
- Lines 102–113 — same metrics in a table with Type/Purpose columns
- Lines 138–146 — prose explanation of each metric

Pick one pass. Either the table or the bullets is enough.

### 4.3 OTLP pipeline depicted twice

[`../../docs_revisited/observability.md`](../../docs_revisited/observability.md) lines 60–71 (ASCII pipeline) and [`../../docs_revisited/architecture.md`](../../docs_revisited/architecture.md) lines 18–30 (Mermaid flowchart) depict the same control-plane topology. Keeping both is fine; the prose around the ASCII block ("Pipeline:") restates what the diagram shows and can drop.

### 4.4 QPU status fields re-listed across files

[`../../docs_revisited/api.md`](../../docs_revisited/api.md) lines 251–266 list 14 QPU status fields as a reference card. [`../../docs_revisited/observability.md`](../../docs_revisited/observability.md) lines 104–113 re-list the same QPU calibration values as metric names.

The doubling is honest but the tone drifts: `api.md` reads like a reference card, the second pass reads like a marketing list. Trimming `observability.md`'s QPU bullets to one sentence plus a pointer to `api.md` would help keep the simple-blunt register.
